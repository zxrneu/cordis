# 生产运行约定

运行时提供容量限制、启动状态检查和有期限的停机等待。它们需要与宿主的请求入口、错误监控及进程管理配合使用；组件 ACTIVE 表示生命周期初始化成功，业务可用性仍由应用的健康检查确认。

## 运行边界

```python
root = Context(max_tasks=512, error_history_limit=128)
root.on("internal/error", report_error)
# 挂载组件或完成 Loader 装配后：
await root.wait_ready(timeout=15)
# 检查业务健康条件后，宿主开始接收请求。
```

容量由整个运行时共享，包含根任务、插件、局部作用域、异步事件回调及定时器。默认 `max_tasks=1024`；达到上限时抛出 `TaskLimitError`，不会隐式建立无限队列。请求入口应据此拒绝、限流或使用应用自有的有界队列。`max_tasks=None` 显式取消限制；生命周期驱动和清理协调不受业务任务额度限制。

`task_count` 提供未完成受管任务数。默认 `error_history_limit=256`，保留最近错误及其所属组件；0 禁用保留，`clear_errors()` 主动清空。`error_count` 是累计报告次数，历史淘汰和清空不重置它。错误历史供短期诊断，持续监控通过同步 `internal/error` 监听器接入标准 logging 或外部监控。异步错误监听器也占任务额度，其失败只记录，避免错误递归。

## 启动与依赖

`wait_ready()` 等待已安排的生命周期稳定后，要求所有期望运行的组件 ACTIVE。缺少依赖或初始化失败立即抛出 `ReadinessError`；初始化迟迟未完成则抛出 `ReadinessTimeoutError`。两者的 `issues` 包含组件、状态、不可用依赖、父组件及原始异常。`cycles` 按服务 Realm 匹配，提供唯一声明提供者之间的环线索；动态提供的服务、多个候选提供者和运行时业务调用环仍需应用排查。

就绪检查失败不会自动卸载插件；宿主可以补充依赖后重试，也可以关闭运行时并拒绝启动。超时或取消不会中断正在执行的初始化。`flush()` 和现有 `Loader.wait_ready()` 仍只等待生命周期推进，不能作为启动成功判据。严格检查从宿主调用，受管任务中调用会触发自等待保护。

## 停机

先停止接收新请求，再从宿主调用关闭：

```python
try:
    await root.close(timeout=20)
except ShutdownTimeoutError as error:
    logger.error("停机超时，清理仍在继续：%s", error.blockers)
    raise
```

`close()` 默认等待 30 秒。超时的 `ShutdownTimeoutError.blockers` 包含未结束的组件、状态和受管任务名。清理仍继续执行，服务在消费者任务退出后才释放。后续 `close()` 等待同一个关闭任务；取消等待者不会取消该任务。清理最终失败会记录到错误历史，后续等待也会收到原来的异常。

`timeout=None` 允许无限等待。任务的 `spawn(timeout=...)` 是卸载时的排空宽限期，过后请求协作取消；`close(timeout=...)` 是调用方的整体等待期限，两者作用不同。插件装卸、配置更新及局部作用域退出仍以完成安全清理为目标。

协程忽略取消、同步阻塞代码、线程或扩展模块不会被这些 API 强制终止。超时依赖事件循环仍能调度；`asyncio.run()` 的最终任务收尾也可能继续等待。进程管理器需设置最终的进程退出期限，并把 SIGTERM / 服务停止请求交给宿主统一处理。

## 更新与验证

初期生产更新使用进程重启或滚动替换。HMR 适合受控开发场景，不能撤销模块导入时已经发生的外部副作用。数据库事务、幂等写入、外部调用补偿由应用负责。

Python CI 配置覆盖 Linux、macOS、Windows 与 Python 3.11–3.14，运行严格类型检查、静态检查和回归测试；独立构建 sdist / wheel，并在隔离环境验证安装后的包及 `py.typed`。CI 配置不等于这些远端组合已运行成功，以实际流水线结果为准。

`tests/test_runtime_limits.py` 覆盖任务容量、错误保留和对象回收、超时后继续清理、等待者取消、依赖异常及反复装卸。200 轮确定性装卸回归检查资源归属与容量恢复，不能替代目标业务的持续负载测试。上线前仍需验证业务峰值、外部服务超时、进程重启恢复及长时间运行的内存趋势。

## 默认行为变更

已有无参 Context 现在采用有限的任务与错误历史容量，`close()` 采用 30 秒等待期限。依赖全部错误历史的应用应接入错误监听器；需要更高并发时显式调整容量；确需无期限等待时使用 `close(timeout=None)`。普通插件和资源管理接口保持原有形式。
