### B01：消费者换 Realm 破坏卸载依赖视图

**位置**：[core.py:997](../src/cordis/core.py#L997)、[core.py:1464](../src/cordis/core.py#L1464)。

**复现**：provider 和 consumer 的 `db` 都绑定共享域 `a`；consumer 的 cleanup 读取 `ctx.db`。只把 consumer 的隔离配置改成 `b`，provider 留在 `a`。

**实际**：cleanup 抛出 `InactiveServiceError`，不能读到 `old`；不捕获时错误进入 `cleanup_error` / `root.errors`，后续 cleanup 业务可能中断。**预期**：旧生命周期的在途任务及 cleanup 仍能使用已提交的 `a` 域服务，卸载完毕才应用新依赖视图。

**原因**：`reassign_context_realms()` 先改当前 Context 的 Realm；`service()` 随后要求它与 `committed_realms` 相同。消费者自己没有搬迁服务，因此不进入更新 `committed_realms` 的分支，保留了旧服务却无法读取。

**修复验收**：在旧/新域都有 provider、只有旧域有 provider 两种情况下换域；旧任务与 cleanup 读旧值，新激活读新值或进入 PENDING。临时可先在旧配置下卸载消费者，再换域重新挂载。

### B02：dispose 与初始化失败并发时留下未移除 Fiber

**位置**：[core.py:755](../src/cordis/core.py#L755)、[core.py:785](../src/cordis/core.py#L785)。

**复现**：异步插件进入 LOADING 并等待 Event；宿主调用 `dispose()`；随后放行初始化，使其抛出 `ValueError`。

**实际**：`await dispose()` 正常返回，但 Fiber 为 `FAILED`、`desired=False`、`uid=1`，仍出现在 `root.fibers`。**预期**：完成已登记的回滚后进入 `DISPOSED`，清除 UID 并从运行时移除；错误仍可报告。

**原因**：`dispose()` 只在等待前检查“无 inertia 的 PENDING/FAILED”；加载失败分支总是设为 FAILED 后返回，不处理已经撤销的 `desired`，等待后也没有补做移除。

**修复验收**：上述竞态一次 dispose 就完成移除，且 cleanup 不重复执行。当前再次调用 dispose 可以移除残留，但不能要求调用者通过重试补齐卸载。

### B03：惯性中断被误当成服务声明违约

**位置**：[core.py:749](../src/cordis/core.py#L749)、[core.py:754](../src/cordis/core.py#L754)。

**复现**：async generator 插件声明 `inject=['db']`、`provide=['derived']`。第一步等待 Event 后 yield 一个逆操作，下一步才提供 derived。等待期间卸载 db provider，再释放 Event；随后重新挂载 db provider。

**实际**：guard 正常阻止下一次迭代，却仍执行 `_check_provides()`，产生 `MissingProvisionError`。插件停在 FAILED，db 恢复后仍不自动激活。**预期**：被目标变化中断的部分初始化应回滚并等待/重算目标；只对完整成功的初始化检查服务声明。

**原因**：检查 provision 发生在判断 `self.target == target and self.desired` 之前。正常生命周期中断走进了失败分支。

**修复验收**：依赖撤销后进入 PENDING，依赖恢复后自动 ACTIVE 并提供 derived；已产生的逆操作执行一次。与 B02 不同，这里 `desired` 仍为 True，插件没有主动抛出错误。

### B04：HMR 回滚后父包属性仍是新版本

**位置**：[hmr.py:234](../src/cordis/hmr.py#L234)。

**复现**：加载普通包的 `pkg.app:app`，v1 提供服务。把文件改成 v2，并让插件初始化抛错；调用 `loader.reload('app')`。

**实际**：服务恢复到 v1，`sys.modules['pkg.app']` 也恢复成旧模块，但 `sys.modules['pkg'].app` 仍是 v2。通过 `pkg.app` 或 `from pkg import app` 读取会继续拿到失败版本。**预期**：回滚后模块缓存与父包的子模块绑定一致。

**原因**：导入候选模块会更新父包属性；`_restore_modules()` 只操作 `sys.modules`，没有恢复这些绑定。此复现不涉及业务自行修改全局变量，而是 Python import 本身维护的模块关系。

**修复验收**：回滚后父包属性与 `sys.modules` 指向同一旧模块；同时覆盖失败导入期间已成功加载的子模块。优先对普通包补齐缓存/父包绑定的备份与恢复。

### B05：取消 HMR 等待会绕过回滚

**位置**：[hmr.py:185](../src/cordis/hmr.py#L185)、[hmr.py:203](../src/cordis/hmr.py#L203)。

**复现**：v1 正常运行；v2 的异步初始化通过 Event 暂停。等 HMR 已卸载 v1 并进入 v2 初始化后，取消执行 `loader.reload()` 的宿主 Task，再让 v2 抛错。

**实际**：取消向外传播，v2 的受 shield 保护的加载继续运行，最终 FAILED；服务为 None，v1 没有恢复。**预期**：候选版本失败时仍完成旧版本恢复，或取消触发受保护的回滚，事务不能停在半替换状态。

**原因**：替换和回滚仅捕获 `Exception`；`asyncio.CancelledError` 不属于它。生命周期加载被 shield，但外层负责检查失败并回滚的事务未受到相同保护。

**修复验收**：候选导入、旧 Fiber 卸载、新 Fiber 加载三个 await 阶段分别注入取消，验证最终是完整提交或完整回滚。当前宿主可持有独立 HMR Task、用 shield 等待，并在取消后继续监督它完成；仅遗弃后台 Task 不算恢复。

### B06：手动卸载不能释放 Fiber 的父级引用

**位置**：[core.py:1228](../src/cordis/core.py#L1228)、[core.py:899](../src/cordis/core.py#L899)。

**复现**：同一个长期存活的 root 下，循环 20 次 `await root.use(...)`、保存弱引用、`await fiber.dispose()`；删除局部引用并执行 GC。

**实际**：`root.fibers` 已为空，但 20 个弱引用全部仍存活；父 Fiber 的 `_actions` 保留了 20 个挂载 Effect。**预期**：手动 dispose 完成后，对应父级清理注册可解除，未被业务引用的 Fiber 能被回收。

**原因**：`Context.use()` 创建的 `remove` 闭包强引用子 Fiber，闭包所属 Effect 挂在父 actions 上；直接 `Fiber.dispose()` 只从 runtime 列表移除自己，没有解除这项父级注册。

**影响**：多次配置替换/HMR 会保留历史 Fiber、Component 和配置对象，直到父生命周期结束。这与已知的 Realm 缓存、错误历史增长是不同的引用链。

**修复验收**：成功手动卸载后弱引用可失效，父 actions 不随累计挂载次数增长；仍由父级触发的卸载保持幂等及正确顺序。

### B07：Effect 错误退出未关闭生成器

**位置**：[core.py:406](../src/cordis/core.py#L406)、[core.py:433](../src/cordis/core.py#L433)。

**复现**：保留一个生成器引用；生成器先 yield 合法 cleanup，再 yield 非法值 `123`，并在 finally 中做清理。把它交给 `root.effect()`。

**实际**：TypeError 已抛出，已登记逆操作执行，但生成器 finally 没执行，生成器仍挂在非法 yield 处。手动 `iterator.close()` 后才执行 finally。**预期**：执行器失败时确定性关闭仍挂起的迭代器，同时回滚已经登记的逆操作。

**原因**：`_execute()` 的 finally 只在 `not guard()` 时调用 close/aclose；`_collect_value()` 抛错时 guard 仍为 True。

**边界**：非法 yield 本身是插件作者错误；这里记录的是运行时处理该错误时漏掉迭代器关闭。已经登记的逆操作没有丢失，也不声称能回收任意未登记的外部副作用。

**修复验收**：同步和异步生成器都覆盖非法 yield，保留外部引用时 finally 也已完成；关闭抛错不能掩盖原始错误或跳过其他逆操作。

### B08：服务清理句柄绕过依赖自等待检查

**位置**：[core.py:514](../src/cordis/core.py#L514)、[core.py:1395](../src/cordis/core.py#L1395)。

**复现**：root 提供 db 并保留返回的清理句柄。声明依赖 db 的 consumer，通过 `ctx.spawn()` 启动任务，任务直接 `await remove_database()`。

**实际**：服务移除触发 consumer 卸载；卸载等待 consumer 的任务排空；该任务又在等待服务移除完成，形成循环等待。复现超时后才释放循环。**预期**：像 `Fiber.dispose()` 的保护一样，在产生变更前抛 `InactiveContextError`。

**原因**：`_Effect.dispose()` 只检查“当前任务属于该 Effect 的 Fiber，且在自己的祖先 sink 内”，没有检查其他 Fiber 的受管任务对这个服务的已提交依赖。服务 remove 又等待所有 affected Fiber。

**边界及验收**：这是对文档已禁止的自卸载调用缺少 fail-fast 防护，不是允许任务自行卸载依赖的新需求。把 service handle、嵌套 Effect 中的 service handle 纳入检查，并在删除服务前拒绝；正常宿主卸载及无依赖任务不受影响。临时做法是把请求交给宿主执行。

## 单独记录的能力边界

**L01：嵌套 group 不参与外层 Loader 的自动 HMR。** 已复现：外层只有 group，其 children 使用字符串定位符，修改子插件文件后，外层 `reload_changed()` 返回 `()`，服务仍为 v1。原因是 [hmr.py:127](../src/cordis/hmr.py#L127) 仅遍历该 Loader 的 `_loaded`，子 Loader 保存在 group 内部。

[HMR API](api/hmr.md) 已明确自动查找“直接管理的条目”，因此这里作为现有能力边界，不算新 bug。若要实现整棵配置树的热更新，需要遍历子 Loader、定义嵌套条目标识和事务范围。

未将以下已说明的行为算作新增 bug：`once()` 使用异步包装而不能搭配 bail；`set()` 不自动重启消费者；假值 Realm 的特殊处理；validate 在再次激活时可能再次执行；动态 import、文件监听错误恢复和任意进程全局副作用的限制。这些选择是否要调整，可单独作为 API/能力改进讨论。

1. B01、B03：先守住卸载依赖视图和响应式恢复。

修复后把对应复现改成正常通过的回归测试，并运行原有完整测试集。此清单是本轮有证据的问题集合，不代表其余路径均无缺陷。
