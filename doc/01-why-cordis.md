# 01. 为什么需要 Cordis

## 1. 现代应用架构的扩展性困境

在构建复杂的企业级系统、机器人框架（如 Koishi）、富客户端开发工具、微内核架构以及插件化平台时，开发者始终面临一个核心矛盾：**系统的灵活性、动态性与稳定性之间的平衡**。

传统的软件工程体系为我们提供了多种组织复杂代码的模型，如控制反转（IoC）、依赖注入（DI）以及事件驱动机制（Event Bus）。然而，当我们将这些模式应用于现代长生命周期、动态插件化场景时，传统方案普遍暴露出致命缺陷。

---

## 2. 传统 IoC / DI 框架的局限性

主流的企业级 IoC 框架（如 Spring、NestJS、InversifyJS 等）以及常见插件体系（如 VS Code 扩展系统、Webpack 插件）的设计大多基于**静态单向启动**假定：

```
传统架构：单向且静态
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│  配置解析   │ ──> │ 构建依赖拓扑 │ ──> │ 启动所有组件 │ ──> [运行期不可变]
└─────────────┘     └──────────────┘     └──────────────┘
```

这种模式在动态可插拔场景下存在三个根本性痛点：

### 痛点一：时间维度的缺失（Temporal Dimension）
1. **静态生命周期假定**：依赖注入容器通常在系统启动阶段计算好完整的依赖有向无环图（DAG），并完成实例化。但在现代应用中，**插件和服务是在运行期动态加载、卸载、热重载或重新配置的**。
2. **缺乏响应式依赖联动**：如果服务 A 依赖服务 B，当服务 B 在运行期被禁用、卸载或重启时：
   - 传统容器：A 仍然持有 B 的旧引用，或在调用时抛出未定义异常，甚至导致整个进程崩溃。
   - 传统方案必须依赖开发者手动编写监听代码，管理复杂的重连/降级逻辑，极易出错。

### 痛点二：空间维度的单一（Spatial Dimension）
1. **全局单例与有限的 Scope**：传统容器通常只有 Singleton（单例）和 Request/Transient（请求/瞬态）作用域。
2. **多租户与隔离配置困难**：如果系统需要同时运行两个功能相同但配置不同的插件实例（例如两个针对不同群组的 Bot 实例，分别使用不同的存储策略或限流规则），传统 IoC 必须引入繁琐的 Named Injection 或复杂的 Factory，无法以树状结构派生并隔离配置和环境。

### 痛点三：副作用管控缺失（Side-Effects Chaos）
1. **清理机制不可靠**：一个插件在被加载时，往往会产生大量副作用：
   - 注册事件监听（`eventEmitter.on(...)`）
   - 启动定时任务（`setInterval(...)`）
   - 创建网络连接、开启子进程、操作 DOM 或文件句柄
2. **内存泄漏与幽灵行为**：当插件被卸载或代码热更新时，如果开发者遗漏了任何一个清理动作（例如少调用了一个 `removeListener`），旧代码的闭包将常驻内存，继续响应事件，产生难以排查的“幽灵触发”与内存泄漏（OOM）。

---

## 3. Cordis 的解法：时空可组合性（Spatiotemporal Composability）

Cordis 从底层彻底重构了“上下文”、“服务”与“生命周期”的关系，提出了 **Spatiotemporal Composability（时空可组合性）** 这一全新范式：

```
                    Cordis 的时空可组合架构
  ┌─────────────────────────────────────────────────────────────┐
  │ 空间维度 (Spatial Composability)                            │
  │   Context 原型树 ──> 逐层派生 (ctx.extend)                   │
  │   命名空间隔离    ──> 服务隔离 (ctx.isolate / Realms)        │
  │   配置层级截断    ──> 局部拦截 (ctx.intercept)               │
  ├─────────────────────────────────────────────────────────────┤
  │ 时间维度 (Temporal Composability)                           │
  │   响应式依赖注入  ──> 依赖就绪自动激活，下线自动挂起         │
  │   Fiber 状态机   ──> 6 态流转与惯性锁 (Inertia Lock) 防抖   │
  │   全生命周期追踪  ──> 自动收集并逆序清理所有 Effect 副作用   │
  └─────────────────────────────────────────────────────────────┘
```

### 1. 空间可组合（Spatial Composability）
- **原型链轻量派生**：Cordis 的 `Context` 是基于 JavaScript 对象的原型链（`Object.create()`）构建的。父子上下文之间继承属性，但子上下文的隔离修改不会污染父级。
- **服务隔离（Isolate）**：通过 `ctx.isolate('database', label)` 可以将特定服务按命名空间划归隔离域，实现多模块独立拥有专属的数据库或网络实例，互不干扰。
- **配置拦截（Intercept）**：通过 `ctx.intercept('service', config)` 可以在当前上下文层级覆写下游所有插件对该服务的配置视图。

### 2. 时间可组合（Temporal Composability）
- **响应式依赖注入（Reactive DI）**：插件只需声明 `inject: ['database', 'http']`。当所需服务存在且就绪时，插件自动执行；任何一个依赖被卸载时，插件自动销毁并回退至 `PENDING` 挂起状态；当依赖重新提供时，插件自动无缝重启。
- **惯性锁与防抖（Inertia Lock）**：在复杂的异步启动/销毁流程中，Cordis 采用内置的惯性锁机制，确保无论并发触发多少次配置更新或服务重载，异步状态都能严格按序切换，绝不产生竞态条件。

### 3. 全托管的副作用收集（Automatic Effect Management）
- 在 Cordis 中，一切副作用均通过 `ctx.effect()` 被当前的 `Fiber` 捕获：
  - 注册事件：`ctx.on()` 返回可销毁句柄，自动登记。
  - 定时器：`ctx.timeout()` / `ctx.interval()` 在上下文卸载时自动清理。
  - 生成器支持：插件支持 `function*` 和 `async function*`，使用 `yield () => cleanup()` 即可声明销毁逻辑。
- 当插件卸载或更新时，**所有副作用自动按逆序（LIFO）完全释放**，从根本上杜绝悬挂回调与内存泄漏。

## 4. 架构范式对比

| 特性维度 | 传统 IoC / 插件系统 (如 Spring, Nest, Webpack) | Cordis 元框架 |
| :--- | :--- | :--- |
| **生命周期** | 静态单向初始化，运行期难以安全插拔 | 完全动态，支持任意时刻挂载、卸载、热重载 |
| **依赖解析** | 启动期一次性生成静态依赖图 | 响应式动态追踪，依赖缺失挂起，依赖恢复唤醒 |
| **上下文结构** | 扁平容器或有限 Scope | 原型链树状上下文（Context Tree），支持多层派生 |
| **空间隔离** | 依赖复杂工厂或 Named Token | 原生 `ctx.isolate()`，支持服务命名空间与多租户 |
| **副作用清理** | 开发者手动编写 `onDestroy` 钩子，极易遗漏 | 框架级自动收集所有 Event/Timer/Resource，自动逆序释放 |
| **热重载支持** | 通常需要重启整个进程或容器 | 基于 ESM 劫持与依赖图推演的零中断精确 HMR |
| **配置动态化** | 静态配置文件或冷加载 | 声明式拓扑树，配置文件双向同步、动态补丁 |

---

## 5. 小结

Cordis 不仅仅是一个依赖注入工具，而是一个**专为高动态、长运行、插件化系统量身定制的底层操作系统**。它将“空间隔离”与“时间响应”内化于框架的核心抽象中，让开发者能够以极具表现力的方式构建模块解耦、自动恢复、易于测试的现代化 JavaScript / TypeScript 应用。
